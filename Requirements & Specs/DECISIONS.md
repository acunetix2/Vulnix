# Architecture Decision Record Log

Record material decisions here. Do not silently change a decision that affects data, security, API compatibility, or deployment.

## ADR-001 — Deterministic scanners plus AI assistance
**Status:** Accepted, revised by ADR-014 (the AI agent is the scanner; these tools are opt-in)  
**Decision:** Use established static-analysis, secret-detection, and dependency tools to generate evidence. Use AI to explain, prioritize, and suggest remediation.  
**Reason:** General-purpose language models can miss vulnerabilities and hallucinate findings; deterministic evidence improves traceability.  
**Consequences:** Scanner adapters and normalized findings are core architecture. AI output must be schema-validated and labelled.

## ADR-002 — Never execute uploaded project code
**Status:** Accepted  
**Decision:** The MVP analyzes files using fixed scanner tools and does not execute submitted code, tests, build steps, or package scripts.  
**Reason:** User-controlled code is untrusted and may compromise workers or infrastructure.  
**Consequences:** Some runtime vulnerabilities cannot be detected. Dynamic analysis is out of scope until a separate sandbox design is approved.

## ADR-003 — Separate API and scan workers
**Status:** Accepted  
**Decision:** Run scans asynchronously in isolated workers, separate from the public API.  
**Reason:** Scanning is resource-intensive and parses attacker-controlled input.  
**Consequences:** Queue state, retries, cancellation, and idempotency must be designed and tested.

## ADR-004 — Minimize source sent to AI
**Status:** Accepted  
**Decision:** Send only the smallest relevant code excerpt and finding evidence after redaction. Do not send the entire repository by default.  
**Reason:** Source code can contain proprietary logic and credentials.  
**Consequences:** Explanations may have limited context; the UI must state uncertainty.

## ADR-005 — Private by default
**Status:** Accepted  
**Decision:** Projects, uploads, scans, findings, and reports are private to authorized workspace members.  
**Reason:** Source code and vulnerability data are sensitive.  
**Consequences:** Tenant authorization tests are release-blocking.

## ADR-006 — Proposed stack
**Status:** Proposed  
**Decision:** React/Vite frontend, FastAPI API, PostgreSQL, Redis-backed queue, object storage, isolated Python worker.  
**Reason:** Clear boundaries, mature libraries, and straightforward local development.  
**Next step:** Confirm deployment constraints and team familiarity before locking the stack.

## ADR-007 — Integrations: persisted outbox, guarded egress, write-only secrets
- **Status:** Accepted
- **Context:** Slack, Jira and webhook delivery make Vulnix the party that opens a connection to a target chosen by a workspace member. That is the classic shape of an SSRF risk, an credential-leak risk, and an at-most-once-delivery risk all at once, on top of a product requirement not to fabricate capability in the UI.
- **Decision:**
  1. Outbound delivery is off unless `VULNIX_INTEGRATIONS_ENABLED=true`, and turning it on requires `VULNIX_INTEGRATION_SECRET_KEY`; the API refuses writes with `409 INTEGRATIONS_DISABLED` or `503 INTEGRATION_KEY_MISSING` otherwise. The address guards apply whether or not delivery is enabled.
  2. Every egress target is normalized (HTTPS only, ports 443/8443, no credentials in the URL) and resolved, then refused if any answer is private, loopback, link-local, multicast, reserved, unspecified, CGNAT (`100.64.0.0/10`) or IPv4-mapped from one of those. Re-resolved on every attempt, with redirects and ambient proxy settings disabled.
  3. Credentials are stored Fernet-encrypted per workspace, with a SHA-256-derived key so any passphrase works. The API is write-only: responses carry `configured` and a last-four-character hint, never the value. Audit metadata records provider, host and booleans only.
  4. Delivery is a persisted outbox: one `integration_deliveries` row per (event, target), claimed atomically, retried with exponential backoff capped at one hour, and parked as `dead` when the attempt budget runs out or the failure was terminal. Redelivery is an explicit operator action.
  5. Event payloads are built from identifiers and counters. Free text from project names, finding titles or scanner output is whitespace-normalized, redacted and clipped to 300 characters before it is queued. Provider error strings are sanitized to `[a-z0-9_]` before they become codes.
  6. Jira opens one issue per completed scan above a configured severity floor. There is no per-finding ticketing, no status sync and no transitions.
- **Alternatives considered:** calling providers synchronously inside the API request (a slow or hostile target would hold a worker and no retry state would survive a crash); a separate message-broker queue only, without a durable row (loses the audit trail and the dead-letter review surface); OAuth connect flows for Slack and Jira (adds a secret-bearing redirect and token refresh surface that the MVP scope does not need — a bot token and an API token cover it; **reversed by ADR-010**, which keeps every guard in this record and puts a consent window in front of them); `VULNIX_ALLOW_PRIVATE_TARGETS` defaulting to on for convenience (kept, but off by default and documented as development-only).
- **Security implications:** an authenticated member can make Vulnix POST to an arbitrary public HTTPS endpoint; the guard reduces this to public addresses but cannot eliminate it — a DNS name that resolves publicly at check time can rebalance to an internal address before the request is sent (residual TOCTOU), and a legitimately public target can still be used as a relay. This is why the feature is opt-in per deployment, why the payload is redacted and capped, and why no URL query string, body or credential is ever logged. Worker egress rules remain the second line of defence.
- **Consequences:** the console can state real connection state (`Live`, `Configured, paused`, `Not connected`) and a genuine delivery log with retryable dead letters; integrations need a running worker or eager mode to deliver, and a deployment without the secret key cannot store credentials at all. GitHub and PagerDuty stayed unimplemented at the time and the UI said so; GitHub was implemented under ADR-010, PagerDuty still has no code behind it.
- **Date / owner:** 2026-10-22 / integrations work on the console redesign.

## ADR-008 — AI model selection from a probed catalog
- **Status:** Accepted, revised by ADR-015 (failover now wraps any primary, hosted included, and triggers on a context overflow as well) and by ADR-017 (the local reviewer this record made the default is no longer offered unless a deployment opts into it)
- **Context:** AI explanation is the product's main function, and the deployment that shipped could only talk to a local Ollama: `ai_provider` was a `Literal["ollama","none"]`, the Groq credential was declared in config and never read, no client could choose a model, and the stored explanation recorded `settings.ai_model` — the name configured at boot — while discarding the `usage` the provider returned. AGENTS.md forbids accepting arbitrary AI model names from clients, which appears to conflict with letting a user switch models. Separately, a user asking for "llama or qwen" on this Groq account gets a truthful answer that is not what they expected: `GET /models` on the key exposes no general Llama chat model, only 512-token `llama-prompt-guard` safety models.
- **Decision:**
  1. The catalog is discovered, not asserted. Each provider's own list endpoint (`GET /models` for Groq, `GET /api/tags` for Ollama) is probed and intersected with a static candidate list, cached for 60 seconds behind a lock, and capped at 24 entries. A model that the provider did not report cannot appear in the UI.
  2. Clients send only an opaque entry id (`"provider:model"`). It is re-validated against the live catalog on every write *and* every call, so an un-pulled local model or a key that lost access fails closed (`422 AI_MODEL_UNAVAILABLE`) instead of reaching a provider with an invented name.
  3. Groq became a first-class primary (`ai_provider` accepts `groq`) and stays the failover target. One credential serves both roles — `ai_api_key` or `ai_fallback_api_key`, whichever an operator filled in — rather than asking for the same secret twice. *(Revised by ADR-015: each hosted reviewer has its own credential and a key is never shared between providers.)*
  4. A stored explanation records the model that answered, not the one that was asked: `provider`, `model`, and `model_id` are kept side by side, and the UI names the substitution when they disagree. Failover wraps only a local primary. *(Revised by ADR-015: the chain wraps a hosted primary too.)*
  5. Failover triggers on `AI_UNAVAILABLE` and `AI_MISCONFIGURED` only. A reply that is unparseable or fails schema validation is a model-quality problem and is reported as `502 AI_INVALID_OUTPUT`, never quietly retried against a different provider. *(Extended by ADR-015: `AI_CONTEXT_OVERFLOW` also hands over — it is a property of the reviewer's window, not of the reply. `AI_OUTPUT_TRUNCATED` joins `AI_INVALID_OUTPUT` as never re-asked elsewhere.)*
  6. Every attempt writes one `ai_usage_events` row. The daily quota is `COUNT`ed from those rows instead of an in-process counter, so a restart cannot reset an allowance and the credit history and the quota are the same fact. Failed attempts consume quota but earn no credit.
  7. The usage table stores counters and identifiers only — never a prompt, snippet or output — which is what makes reading a year of rows in one query safe.
- **Alternatives considered:** a hardcoded model list in config (goes stale silently, and offers names this account cannot serve); accepting a raw model string with a regex allowlist (satisfies the letter of the rule while letting a client steer a provider); a per-provider "is this model good at code" rating computed server-side (unverifiable, and would read as an assurance the product cannot give); keeping quota in memory with the heatmap derived from it (a restart would hand out a fresh allowance and the two numbers would disagree); showing the whole provider list rather than the candidate intersection (Ollama's tag endpoint returns embeddings and utility models the reviewer cannot use).
- **Security implications:** probing a provider's list endpoint means the Groq key is sent on every catalog refresh, so a hosted credential leaves the process at the same rate as the explanations themselves; the probe result is cached to bound that. Model identity is written to the audit log, never prompt content or the credential. Nothing about a provider's error body reaches the client: transport failures collapse to a fixed message, so an internal hostname in a URL cannot leak through an error string.
- **Consequences:** availability answers "which models can I switch to", so the honest answer is "fewer than the marketing page claims" — this account offers Qwen 3.8 27B and two GPT-OSS sizes, and no Llama chat model. The picker can be empty, and the UI says why instead of showing a disabled control. A local primary that is slow costs the caller the primary's timeout before the hosted answer arrives. Credits are now real and per-user, so quota values need operator review per deployment.
- **Date / owner:** 2026-10-22 / making AI review work with a switchable hosted model.

## ADR-009 — Account identity: Vulnix owns the name, the provider owns the credentials
- **Status:** Accepted
- **Context:** The console had no account surface — the topbar avatar mounted a menu label without the group ancestor Base UI requires, which threw and blanked the page, so the menu a user saw as "dead" was a crashed app. There was also nowhere to see which workspaces one belonged to, no way to change the name the audit trail attributes decisions to, and no password route at all, which Settings had to state as an unavailable feature. Auth itself is a Supabase GoTrue proxy: Vulnix verifies the access token and keeps no session of its own, and the local `users` row mirrors only `id`, `email` and `display_name`.
- **Decision:**
  1. `users.display_name` is the name the console shows and the audit records. `GET /auth/me` upserts the verified JWT subject into `users` and returns it beside the workspace roles read from the membership table — roles come from rows Vulnix owns, never from a client-supplied claim.
  2. `PATCH /auth/me` writes locally and is the only profile write Vulnix makes. It takes a 1–120 character name trimmed in a *before* validator, so a value of spaces is a validation error rather than a blank profile that renders as an empty header.
  3. `PUT /auth/password` forwards the new password to the identity provider using the bearer token already on the request. Vulnix neither stores nor hashes it, reads only `body.password`, and discards it; nothing is echoed back.
  4. Email, sign-in provider and every other credential attribute stay read-only here. The console's own sign-out clears this browser's token and says so rather than implying a provider-wide revocation.
  5. Credential changes are throttled (5 per user per 15 minutes) because a stolen session should not be able to lock the owner out repeatedly. Other `/auth` reads are not.
  6. No migration. `display_name` already existed on `users`; the decision was which store is authoritative, not which column to add.
  7. After a rename the console re-reads `/auth/me` so the header follows without a reload, and the avatar monogram derives from the name rather than the mailbox prefix, which is the only part of the identity a user can edit at widths where the name label is hidden.
- **Alternatives considered:** keeping the name in Supabase `user_metadata` (turns every rename into a provider write and makes a displayed name depend on provider availability); storing a password hash in Vulnix (a second credential store that can silently diverge from the one that actually authenticates, and is never consulted); returning workspace roles as JWT claims (the client could assert `owner`); putting the editor on the Settings tab (two places that write one field, and Settings exists to state what a deployment *cannot* do); a provider-side password reset link only (correct for a lost password, useless for a signed-in owner who wants to rotate one).
- **Security implications:** the password crosses the boundary once, over TLS, with the caller's own token — so the risk is not storage but leakage through logs and error bodies. Neither the request body nor the provider's error payload reaches a log or a response: transport failures collapse to a fixed message and provider statuses map to a sanitized detail. The in-process limiter resets on restart and is per-worker, which bounds it to abuse-of-one-session rather than a distributed guarantee. A deployment running with `auth_disabled` gets the dev user's row, so the endpoint's behavior there is development-only and the test that asserts `401` forces auth on.
- **Consequences:** renaming is instant, offline-tolerant and survives provider outages; the profile page can show real workspace roles. The password form only renders when `/ready` reports `supabase_auth: configured`, and a rotation here does nothing about a lost password — that flow stays with the provider's reset link. Settings' earlier "no password-change route" claim is now false and was replaced with a pointer to the profile page.
- **Date / owner:** 2026-10-22 / account page and topbar menu.

## ADR-010 — Consent windows replace pasted credentials; connections are a separate table
- **Status:** Accepted (supersedes the OAuth clause in ADR-007's alternatives)
- **Context:** Every integration in the console was a form with a secret field, and the brief for this round was that a 2026 user should not be pasting API keys at all: link the account, approve in the provider's own window, and let the backend hold the credential. ADR-007 had rejected OAuth for Slack and Jira on the grounds that a bot token and an API token covered the MVP; that rejection is what this record reverses, for those two providers plus GitHub, which was until now labelled "not implemented" in the UI. OAuth also brings the two things ADR-007 was avoiding: a redirect endpoint that accepts a credential nobody authenticated at, and a long-lived token that has to be renewed.
- **Decision:**
  1. A connection is made in the provider's window. The console calls `POST /{workspace}/integrations/{provider}/connect`, which returns a compiled-in authorize URL with a signed state; nothing is stored and nothing is sent outbound at that point. Client id and secret exist only in the environment, and are never in a response, the console, an audit row or a log line.
  2. Consent state is an HMAC-signed, expiring link (default 600s) carrying provider, workspace, actor and nonce, keyed on `VULNIX_INTEGRATION_SECRET_KEY` and compared in constant time. Single use is best-effort in-process; the real bound is the provider, which refuses a second exchange of the same authorization code, and the short TTL.
  3. Tokens live in a new `oauth_connections` table, one row per (workspace, provider), Fernet-sealed the same way `integration_configs.secret_enc` is. Kept separate on purpose: `integration_configs` means "where to send", `oauth_connections` means "who approved, to what scope, until when". Splitting them avoided changing the `provider IN ('slack','jira')` CHECK and its constraint name under a migration.
  4. One precedence rule, everywhere: a consented token is used and a hand-pasted secret is the fallback for the deployments where a consent window is impossible (self-hosted Jira). `configured` is true when either exists; disconnecting deletes the connection *and* clears the stored secret, because a revoked consent must not keep delivering through the leftover credential.
  5. No client-supplied value names a host or a target. Authorize, token and resource URLs are constants. A Jira site is chosen by `site_id` from the provider's own accessible-resources list (`JIRA_SITE_NOT_GRANTED` otherwise); a GitHub import names only a repository id from the allowlist the workspace stored (`GITHUB_REPO_NOT_SELECTED` otherwise); a repository name and ref are shape-checked before a connection is opened, and the zipball redirect's `Location` is re-passed through the egress guard rather than followed.
  6. A repository import is not a second scan path. The archive is streamed into `storage.put_stream` under `upload_max_bytes`, magic-checked, and recorded as an ordinary quarantined `Upload` under the same per-user quota, so extraction validation and the existing scan pipeline are the only consumers. No cloning, no execution — ADR-002 stands.
  7. Renewal is silent and its failure is explicit: an expired access token with a refresh token is renewed and re-sealed (Jira rotates it, so the new pair replaces the old); without one the connection reports `OAUTH_CONNECTION_EXPIRED` and asks to be redone rather than being retried forever. Undecryptable tokens report `OAUTH_TOKEN_UNREADABLE`, which is a key rotation and cannot be fixed by the user.
  8. Setup after a consent is not gated by the delivery switch. A configuration write that carries no secret needs only `INTEGRATION_SECRET_KEY`, not `INTEGRATIONS_ENABLED`, because choosing a channel or a project sends nothing. The exchange at the callback posts to fixed provider hosts, so the workspace-controlled SSRF surface ADR-007 was guarding does not grow.
  9. The last pasted secret left the UI: Vulnix generates a webhook signing key on create, returns it once, and offers rotation. A receiver that minted its own can still supply it.
- **Alternatives considered:** keeping tokens in `integration_configs.config` (puts a secret in the column documented as non-secret and makes every read a leak); a device flow (needs a polling endpoint and a second screen, and none of these three providers makes it simpler for an admin); letting the console pass a clone URL or repository URL (arbitrary-host fetch, exactly the surface ADR-007 exists to prevent); a durable `oauth_states` table for strict single use (a second table plus a pruning job, for a guarantee the provider already gives on the code itself); a GitHub App with per-repository installation (the right shape for an org-wide product, but requires installation admin, a webhook subscription and a PEM signing key for this MVP's Connect button); asking the user to keep pasting a PAT behind a "classic" toggle (a second path to test and a second way to be wrong).
- **Security implications:** the callback is unauthenticated by design, so the signed state is the only authority it has; a forged or expired state, or one naming a different provider than the path, ends in a redirect with `oauth_error` and stores nothing. Whoever clicks Connect decides which external account gets linked, so the console always shows `account_label` returned by the provider and offers Disconnect; a mistaken link grants nothing beyond what that account already holds. Tokens are decrypted only at the moment of a provider call and never appear in a response, an audit row or a log. Egress is still opt-in for everything that *sends*: the same normalize-and-resolve guard runs on provider calls, and `follow_redirects=False` plus `trust_env=False` on every one of them.
- **Consequences:** three real integrations instead of two, and GitHub scanning exists, so the console's "Not implemented" language is now only true of PagerDuty. Operators must register one OAuth app per provider and set `VULNIX_OAUTH_REDIRECT_BASE_URL` plus `VULNIX_CONSOLE_BASE_URL`; until they do, providers report `oauth_available` false with a reason and the UI shows no dead button. The schema gained a table and a migration; revocation and expiry became failure modes the API has to name. Repository archives consume the same storage and quota as uploads, so a large monorepo is a quota decision rather than a code problem.
- **Date / owner:** 2026-10-22 / integrations round of the console redesign.

## ADR-011 — GitHub is integrated as a GitHub App, using its user access tokens
- **Status:** Accepted (reverses the GitHub App rejection recorded in ADR-010's alternatives)
- **Context:** ADR-010 shipped the GitHub consent as a legacy OAuth app asking for the `repo` scope, and rejected a GitHub App on the grounds that it needs installation admin, a webhook subscription and a PEM signing key. The deployment then moved to a GitHub App anyway, because GitHub is the primary code source and the same credential also has to serve sign-in: one app can register several callback URLs, so it covers both the repository integration and Supabase, which two separate OAuth apps cannot. That move broke the consent window — GitHub answered "The redirect_uri is not associated with this application", and the code was still sending a `scope=repo` parameter a GitHub App does not accept.
- **Decision:**
  1. The credential stays a GitHub App, and we use its **user access token** flow. That is the part ADR-010's objection was about: no PEM, no installation token, no webhook subscription, and no per-installation admin beyond the user clicking Install. The authorize and token endpoints are the same two URLs an OAuth app uses; only the parameters and the token's lifetime differ.
  2. No `scope` parameter is sent for GitHub, and `OAUTH_APPS["github"].scopes` is empty. A GitHub App's permissions (Contents and Metadata read-only, Email addresses read-only for Supabase profile lookup, and Pull requests read-write once the agent opens fix PRs) are declared on the app itself, so a scope in the URL would be asking for something the app cannot grant. Slack and Jira are unchanged — the omission is per app, not global.
  3. The granted scope is recorded only as the provider returned it. `_normalize_tokens` no longer falls back to the compiled-in scope list, because inventing `repo` on the connection row would tell an admin the consent can do something it cannot.
  4. Repositories are listed through the installation — `/user/installations`, then `/user/installations/{id}/repositories` — rather than through `/user/repos`. An app can only read where it was installed, so the wider listing would offer repositories whose archive fetch is then answered `404`: a picker full of dead choices is worse than a short one. Installations are walked as one continuous list so paging still reaches every account, and are capped at 20.
  5. "Expire user authorization tokens" is on. The token then lasts eight hours and rotates, which makes ADR-010's silent refresh the normal path for GitHub rather than an edge case; the refresh token is re-sealed on every renewal, exactly as Jira's rotation already required.
- **Alternatives considered:** a legacy OAuth app alongside the GitHub App used for sign-in (two credentials to keep in sync, and the `repo` scope is coarser than Contents read-only on chosen repositories); installation access tokens with a PEM (what ADR-010 actually rejected — a signing key, a webhook and an installation lookup per call, for no gain while the reviewer only reads archives); keeping `/user/repos` and treating a `404` zipball as a skipped repository (hides a configuration problem as an empty audit); asking the operator for a classic PAT instead (ADR-010 already rejected the pasted-credential path).
- **Security implications:** strictly narrower than what it replaces. `repo` on an OAuth app is every repository the consenting user can reach, including ones nobody chose; Contents read-only on an app is the repositories its installation was granted, and the workspace's stored allowlist narrows that again before any fetch. The listing change means the console can no longer name a repository the credential cannot read, so a stale allowlist entry fails at selection time rather than at scan time. Nothing else moved: the signed state, the egress guard, `follow_redirects=False`, and the sealed-token storage are all ADR-010's and unchanged. An app that is installed nowhere lists nothing, which reads as "not set up" rather than as an empty repository.
- **Consequences:** operators register a GitHub App instead of an OAuth app, grant Contents and Metadata read-only plus Email addresses read-only for Supabase profile lookup, and register two callback URLs — `{base}/api/v1/integrations/oauth/github/callback` and the Supabase project's `/auth/v1/callback` — with the first matching character for character. `GET …/integrations/providers` now reports `scopes: []` for GitHub, and `GET …/integrations/connections` reports an empty granted scope for it. The eight-hour token makes the refresh path load-bearing for GitHub, so a failed renewal surfaces as `OAUTH_CONNECTION_EXPIRED` after a working day rather than at connect time. Adding Pull requests read-write is what unblocks the agent's own fix PRs, and is a permission change on the app rather than a code change.
- **Date / owner:** 2026-10-23 / GitHub integration.

## ADR-012 — Autonomy means bounded, evidence-checked investigation
- **Status:** Accepted (resource defaults revised by ADR-013)
- **Context:** The first agent-first scanner made one isolated model call per file. That gave every file a verdict but could not follow an input into a helper, check a caller's authorization guard, or discard a hypothesis after seeing the surrounding implementation. Making the model autonomous by giving it shell or filesystem access would conflict with ADR-002 and turn an untrusted archive into executable instructions.
- **Decision:** keep the initial per-file review, then permit a small investigation loop driven by a provider-neutral JSON protocol. The only actions are `read_file` and case-insensitive literal `search`, executed by the server against the already validated source-file manifest. Reads return bounded, numbered windows; search returns at most eight leads. A finding may name a related file only after a real code view supplied its whole cited range. The visibility snapshot belongs to the last successful answer, so a failed later call cannot retroactively validate an earlier guess. A failed follow-up preserves that answer and its supported findings. Per-file turns, audit follow-ups, context files, related-file bytes, total calls, time and credits are bounded independently.
- **Alternatives considered:** provider-specific function calling (would split behavior between local and OpenAI-compatible providers); replaying the whole conversation on every turn (too large and slow for small models); allowing arbitrary tool names or paths (shell/SSRF/filesystem risk); accepting search-hit evidence directly (a match is not enough context for a security verdict); replacing the initial review with an open-ended agent loop (could spend the whole budget on one file and leave the rest unread).
- **Security implications:** repository code, search results and prior model output remain untrusted data. There is no shell, repository execution, package installation, browser, arbitrary filesystem read or network tool. Search is literal rather than regex. The server builds suggested patches only from archived lines it can match exactly, and this loop still never applies, commits or pushes anything.
- **Consequences:** reviews can confirm or reject cross-file hypotheses instead of commenting on dangerous functions in isolation. Initial repository coverage remains the default because follow-ups have a separate allowance inside the total call budget. The audit record exposes investigations, follow-ups, reads, searches and follow-up failures, and each investigation appears in the live step trace. More capable behavior comes from the loop and evidence checks rather than from a particular model name.
- **Date / owner:** 2026-10-24 / autonomous agent review.

## ADR-013 — Agent coverage and investigation budgets are opt-in
- **Status:** Accepted
- **Context:** ADR-012 shipped conservative defaults of 40 files, 12,000 bytes per file, 52 total calls, two investigation turns per file, 12 follow-ups per audit, three context files and 3,000 related-file bytes. Those ceilings can stop a security review before it has followed the available evidence. The requested default is comprehensive agent review rather than a shallow first pass, without weakening the repository trust boundary.
- **Decision:** every `agent_max_*` coverage/investigation setting and `agent_related_file_bytes` now defaults to zero, meaning no limit in that dimension. A positive value remains an operator-configured cap. Zero no longer means an empty intake, an unusable read window or a disabled investigation. Duplicate-request detection still stops repeated evidence loops, and each action retains its deterministic result shape. The separate scan wall-clock deadline, provider timeouts, AI rate limit and daily credit quota are unchanged.
- **Alternatives considered:** merely changing the configuration values to zero (would have skipped all files and made reads fail); removing the settings and every cap (would deny operators a way to control cost and would conflate safety bounds with coverage budgets); removing the scan deadline and AI quota as well (outside the requested coverage change and separately controlled); raising the old constants to larger guesses (still truncates some repositories without making the contract explicit).
- **Security implications:** no safety boundary is relaxed. Reads still resolve only against validated intake files, search remains literal, cited ranges still require a real code view, and repository code is never executed. Larger and longer reviews can send more source to the configured model and consume more credits, so deployments that need a spending ceiling must set the existing quota or positive agent budgets deliberately.
- **Consequences:** by default the agent can select every eligible source file, keep full file content, read any number of manifest files and continue distinct investigation turns until it finishes or an independent deadline/quota stops it. Existing positive-limit tests and deployments retain their behavior. Operators can restore any former cap with the corresponding `VULNIX_AGENT_*` variable.
- **Date / owner:** 2026-10-24 / comprehensive vulnerability review.

## ADR-014 — The AI agent is the scanner; CLI analysers are opt-in extras
- **Status:** Accepted
- **Context:** ADR-001 assumed deterministic tools produced the evidence and AI assisted it. The product now reviews code the way a senior security engineer does: the agent forms hypotheses, reads source, follows data flows across files and reports only findings it can cite. `ScanOptions` still defaulted `static_analysis`, `secrets` and `dependencies` to `true`, and `build_adapters()` used `.get(key, True)`, so every audit launched semgrep, bandit, gitleaks, pip-audit and trivy as required stages. On hosts without those binaries the execution stream filled with `TOOL_UNAVAILABLE` and `EXEC_FAILED` rows, which made an autonomous agent look like a wrapper around command-line tools.
- **Decision:** the three CLI categories now default to `false` in both `ScanOptions` and `build_adapters()`, so an audit that asks for nothing runs the agent alone; a persisted scan record that explicitly enabled a category keeps it. `agent_review` stays default-on. `_decide()` adds `NO_ANALYSIS_REQUESTED` for the case where the agent was turned off and no CLI category was requested, instead of reporting `ALL_SCANNERS_FAILED` against tools that were never asked for. The adapters themselves are unchanged and remain available when requested. The New Audit form starts with only AI review enabled and labels the rest optional, and the audit detail states when no CLI tool was asked for.
- **Alternatives considered:** deleting the adapters (removes the operator's ability to add deterministic corroboration, and normalization and provenance already depend on them); running tools but hiding their rows from the trace (the failure would still be real and would still spend worker time); leaving the defaults on and filtering status upstream (the API contract, and any non-browser client, would keep launching five processes per audit).
- **Security implications:** no boundary moves. Uploaded code is still never executed (ADR-002), findings are still evidence-bound to lines the model actually saw (ADR-012), and secret redaction before the prompt is unchanged. Because gitleaks and pip-audit no longer run by default, the agent is the only secret and dependency reviewer on a default audit, so intake had to stop discarding the surfaces those tools used to cover: `.md`, `.html`/`.ejs`/`.hbs`/`.pug`, `.json`, `.xml`, `.ps1`, `.properties`, `.proto`, `.graphql`, notebook, Elixir, Dart, Lua, Scala, Groovy, Perl, Kotlin script, Objective-C, Zig and Ruby/TS variants are now reviewable, along with `.npmrc`, `.pypirc`, `.netrc`, `.git-credentials` and suffixed `.env.*` files. Lockfiles, minified bundles, generated trees and `.env.example` remain excluded.
- **Consequences:** a default audit spawns no CLI processes and its tool-run list contains only the agent. Docs/config-heavy repositories that previously failed with `NO_SOURCE` are now read; when an archive genuinely holds no source, the step says so with the candidate count instead of a bare "No reviewable source files". `README` and `API_SPEC` examples that enabled categories are still valid, since they opt in explicitly.
- **Date / owner:** 2026-10-27 / agent-first scanning.

## ADR-015 — A failover chain of hosted reviewers, with the request bounded before it is sent
- **Status:** Accepted (revises ADR-008 decisions 3, 4 and 5, and ADR-013's assumption that one reviewer answers)
- **Context:** One hosted reviewer sat between every audit and an answer. ADR-008 made Groq a first-class primary but kept failover for local models only, and a single `ai_fallback_provider` behind it — so when that key was rate-limited or down, files failed as `AI_UNAVAILABLE` and the retry loop in `app/agent/review.py` re-asked the same dead endpoint once per attempt, up to eight times per file, each time paying its timeout. A file longer than the reviewer's context window was also simply POSTed and lost. Two more free-tier hosted reviewers were requested so an audit can continue when the first is down: Google AI Studio and OpenRouter. The research that named them listed `gemini-1.5-pro` and `gemini-1.5-flash`, which Google has retired; the current free-tier pair is `gemini-2.5-pro` and `gemini-2.5-flash`, and those are what the catalog allowlists.
- **Decision:**
  1. All three hosted reviewers are one adapter. `GroqProvider`, `GeminiProvider` and `OpenRouterProvider` are thin subclasses of `_OpenAIChatProvider`, which holds the request shape, the authorization header, the truncation check and the window guard — because a cap applied to one provider and missed on another is the bug this structure exists to prevent. Each supplies only its own credential, base URL, timeout and context window from `VULNIX_AI_*` settings.
  2. A credential never leaves its provider. `settings.gemini_api_key` reads only `ai_gemini_api_key`; there is no shared-key fallback of the kind ADR-008 decision 3 allowed for Groq, because a Groq key sent to a Google endpoint is both a privacy leak to the wrong vendor and a guaranteed 401 that would be logged as an outage.
  3. The chain is general, not a pair. `_failover_targets()` returns every configured hosted reviewer except the primary: the named `ai_fallback_provider` leads, the rest follow in groq → gemini → openrouter order. Any hosted reviewer can be primary and any can hand over, so the local model → hosted path from ADR-008 and the hosted → hosted path are the same mechanism.
  4. A failed link is parked. `FallbackProvider` marks a provider down for `ai_provider_cooldown_seconds` (60 by default) and skips it while it cools, so an outage costs one timeout per reviewer rather than one per attempt per file. Only a call that answered is ever charged, so the handover itself spends no credit. *(Revised by ADR-016: a reviewer that refuses because the file is too wide for it is not parked — the width is a property of the file, not of the link's health.)*
  5. Links are built lazily. Each non-primary link is a callable that constructs the adapter and resolves its model only when the handover reaches it, so a half-configured or unreachable target cannot break a healthy primary and cannot spend a catalog probe on every request.
  6. The output is bounded. `_chat_payload()` sends `max_tokens = ai_max_output_tokens` (2048) for every hosted reviewer: a review answer is a small JSON object, so a completion running past the cap is a reviewer that stopped following the schema, and paying for the rest of its context would not turn it into a finding. `finish_reason == "length"` raises `AI_OUTPUT_TRUNCATED` and is never re-asked of another reviewer — the cap is the same cap whoever is asked.
  7. The prompt is refused before it is sent. `_approx_tokens()` (four characters to the token) checks the prompt against the reviewer's window minus the output cap, and raises `AI_CONTEXT_OVERFLOW` (413) without opening a connection. A provider would reject the request anyway; sending it would bill input tokens on a guaranteed failure.
  8. A narrow reviewer is a reason to move on, not to give up. `AI_CONTEXT_OVERFLOW` is in `_FALLBACK_CODES`, so a 32k-token OpenRouter model passes a long file to a wider one, and it is in `review.py`'s `_CONTINUE_CODES` but deliberately *not* in `_RETRYABLE_CODES` — the retry loop never re-fires a mathematically guaranteed overflow, and it does keep reviewing the next file, which usually fits.
  9. A handover asks only for a model the account has. `catalog.handover_model()` checks the configured default against that provider's probed listing and falls back to the first reachable entry, so a takeover never burns its single attempt on a name the key cannot serve. OpenRouter is matched on the exact reported id, `:free` suffix included: stripping it would offer a paid model to a free-tier key. *(Revised by ADR-016: when the listing confirms nothing for that provider the answer is `None`, and the link is skipped with no request and no cooldown rather than tried on an invented name.)*
  10. Nothing new reaches a client. Gemini and OpenRouter models appear only as Vulnix aliases (`Vulnix Wide`, `Vulnix Steady`, `Vulnix Sprint`, `Vulnix Focus`) under the existing rule that no provider, hosting or vendor model name reaches a client surface, and `GET /api/v1/ready` adds `ai_hosted_tertiary` beside the existing two slots — credential presence by chain rank, never provider identity. The endpoint is typed `dict[str, str]`, so handover depth is stated as the `ai_fallback` on/off rather than as a number.
- **Alternatives considered:** hardcoding a Groq → Gemini pair (the deployment would need a code change for the third reviewer, and a Gemini primary would have nowhere to go); sending a long file to every link and letting each answer 413 (three billed failures instead of one free refusal); re-asking a dead reviewer on every retry (ADR-008 shipped this for local primaries; with a chain of three it multiplies the wasted timeouts); trusting the pasted research and allowlisting `gemini-1.5-*` (retired, so the account would confirm nothing and the picker would render empty); routing a handover by severity through a second alias-priority table (a wide-context call on every high-severity file is exactly the spending this record is meant to bound, so Wide/Steady/Sprint/Focus stay out of automatic severity routing; that unused duplicate table was later deleted — see ADR-017); a full tokenizer from each provider's package (a heavy per-provider dependency for a check that only needs to be coarse enough to prevent a bill); renaming `providers/ollama.py` to something provider-neutral (eight modules and five test files import from it; the rename would be pure churn — the file's docstring states it holds every adapter).
- **Security implications:** a hosted credential still leaves the process on every request and every catalog probe, now to three vendor hosts instead of one, each keyed separately so no key travels to a host that was not given it. The context guard compares against a *window setting*, not a provider-advertised limit: a window configured too high means a refusal by the provider rather than a leak. Prompt content never reaches a log or a response — the guard logs provider and window size only, `_post()` logs a status code and nothing else, and a provider's error body is discarded before it can echo a prompt. Free tiers are the reason `ai_max_output_tokens` and the cooldown exist: without them, one audit's retry loop can exhaust a per-minute allowance and the failure surfaces as `AI_UNAVAILABLE` rather than as a partial review. All of ADR-002, ADR-004 and ADR-012 still holds — failover moves a redacted prompt between reviewers, it does not execute anything, widen what is sent, or trust model output.
- **Consequences:** an audit now completes on a hosted outage instead of failing, but only if `ai_fallback_enabled` is on *and* a second reviewer has a credential — otherwise the chain is one deep and `ai_fallback` reports `disabled`. Operators must set `VULNIX_AI_{GEMINI,OPENROUTER}_API_KEY`; `.env.example` documents each block and the local env has the names with empty values, so nothing works until the keys are supplied. The smallest configured window governs which files a given reviewer is offered, so a deployment with only OpenRouter behind a Groq failure reviews fewer files per pass. Cooldown means a restored reviewer is not retried for up to `ai_provider_cooldown_seconds`; `reset_provider_health()` and an operator retry clear that. Two retry-loop failure modes are now client-visible and had to be added to the console's error hints. `VULNIX_AI_MAX_OUTPUT_TOKENS=0` restores provider defaults for a deployment that wants longer answers and accepts the billing.
- **Date / owner:** 2026-10-27 / making the reviewer chain survive a hosted outage.

## ADR-016 — A crashed scan is a result, and a reviewer's refusal is not an outage
- **Status:** Accepted (revises ADR-015 decisions 4 and 9; extends ADR-014's failure recording)
- **Context:** A live uvicorn capture of one real audit exposed four separate defects that no test covered. When the database connection died mid-scan, the exception propagated out of the Celery task: the job row stayed `running` forever, the API had already returned 202, and the console showed a scan that would never end — the trace write and the status write both failed on the same poisoned session. The step trace committed `scan.summary` by mutating the dict in place, which SQLAlchemy cannot see on a JSON column, so even a healthy run could lose its steps. On the reviewer side, OpenRouter answered a long file with its own machine-readable `ContextLengthTooLong` reason, and because every non-2xx was read as a configuration failure the chain parked that reviewer for the cooldown and the audit's retry loop then spent seven attempts and 46 seconds sleeping while every link in the chain was benched — making no request at all. A handover could also still name a model the account had never confirmed (`ai_fallback_model` pointed at a Groq tag that account's listing does not contain), so the takeover attempt failed and the surviving link was benched for doing it.
- **Decision:**
  1. A crash is recorded, not rethrown. `execute_scan` catches `Exception`, rolls back the poisoned session, and writes `status=failed`, `error_code=INTERNAL_ERROR` and `completed_at`. The audit was already accepted with 202, so the only honest continuation is a result the console can render.
  2. If that write also fails, it is retried once on a fresh session taken from `SessionLocal()`; if the fresh session fails too, the worker logs the loss and gives up. Never a third attempt: a database that will not accept a status is not going to accept one because the worker insisted.
  3. A finished scan is left alone. Recovery only touches a row still marked `running`, so a retried task cannot overwrite a completed audit.
  4. The step trace reassigns rather than mutates (`scan.summary = {**scan.summary, "steps": …}`) and retries a failed commit once after a rollback, then drops the trace. Observability losing a write must not fail an audit that already produced findings, and the cap (`_MAX_STEPS`) stays so the column cannot grow without bound.
  5. A handover never invents a name. `catalog.handover_model()` returns `None` when the provider's listing confirms nothing, and `_failover_link.build()` raises a `AI_MISCONFIGURED` that the chain recognises as *not* a health signal: the link is skipped with no HTTP request and no cooldown. A skipped reviewer costs nothing; a benched one costs the rest of the audit.
  6. A refusal about width is a property of the file, not of the link. `AI_CONTEXT_OVERFLOW` moves the audit on without parking the reviewer, so the next — shorter — file is still offered to it. Outages, transport failures and misconfiguration still park.
  7. A refusal is classified by the reviewer's own reason code. `_refusal_tag()` reads `error.code`, `error.type` or `error.status`, lowercases it and strips non-alphanumerics, and compares against a set of context-width tags; a match becomes `AI_CONTEXT_OVERFLOW` (413) and anything else stays `AI_MISCONFIGURED` (502). The vendor's message body is logged as a status code and nothing else, and never reaches a client.
  8. The retry loop waits for the reviewer that actually wakes. `retry_wait_seconds(provider)` returns, for a chain, the earliest cooldown end among the reviewers it was handed work by, and the audit sleeps `max(backoff, that)` — the backoff is never shortened, and if the resulting wait would run past the deadline the step fails with "Out of time before the next retry" instead of firing seven requests nobody will answer. The dispatch is a module function with an `isinstance` check rather than a method on the `AIProvider` ABC, because the test suite hands over roughly sixteen duck-typed provider stubs that would otherwise have to grow the method.
- **Alternatives considered:** letting the task raise so Celery marks the job failed (the `scans` row is Vulnix's own and would still read `running` — the queue state is not what the console renders); a periodic reaper that flips stale `running` rows (fixes the symptom on a timer and turns a live audit into a false failure); mutating `scan.summary["steps"]` and flagging the column with `MutableDict` (an extra dependency on every model that reads it, for a write that needs one assignment); classifying refusals by the vendor's human-readable message (the wording changes per tier and per region, and matching on it would put a provider's text into a code path); putting `next_open_seconds()` on the `AIProvider` ABC (correct shape, but it breaks every stub in four test files for no production benefit); parking the narrow reviewer anyway and letting the cooldown expire (this is what shipped before, and it is what turned one long file into a chain-wide stall).
- **Security implications:** the refusing reviewer's body can carry request metadata, an internal host, or a fragment of what was sent — so only a short allowlisted tag is ever read from it, the tag is used for classification only, and the client receives fixed text plus a code. Logs carry provider name, HTTP status and the tag, never the body, the prompt or the credential. Recovery writes only status columns on the caller's own scan row, on a session taken from the pool, so no query built from scan content is involved. Nothing here widens what leaves the process: the skip-on-nothing-confirmed rule sends fewer requests than before.
- **Consequences:** a dead connection produces a failed audit the console can show instead of a permanent `running` row, and one existing zombie in the development database had to be corrected by hand. Two client-visible behaviours changed: `AI_CONTEXT_OVERFLOW` can now come from the reviewer's own reason code rather than only the pre-send guard, and a chain no longer benches a free-tier reviewer for a file it cannot hold. The wait-reconcile means a retry can sleep up to a full cooldown, which is bounded by the audit deadline and now reported rather than discovered afterwards. A vendor that refuses without a machine-readable tag is still treated as misconfigured — the conservative direction, and the one that keeps parking.

## ADR-017 — Local inference is retained but no longer offered
- **Status:** Accepted (revises ADR-008, which made the local reviewer the default)
- **Context:** ADR-008 put Ollama first in the catalog and made it the boot default because that was the only endpoint this deployment could reach at the time. As the reviewer chain became hosted, the local entry turned into a liability rather than an option: a picker that lists whatever the host happens to have pulled invites a workspace to select a reviewer that then cannot answer, the local model's window and CPU latency dominate an audit's timing, and "runs where your code lives" is not the product being shipped. The user asked to remove the local model "for now", which is a withdrawal from the offered surface, not a deletion of the adapter.
- **Decision:**
  1. `ai_local_enabled: bool = False` gates `_probe_ollama()`. With it off, `GET /api/tags` is never requested — the listing is not asked for and then filtered, it is simply not asked. One setting restores the whole local path: adapter, aliases, window and thinking controls.
  2. The boot default reviewer is a hosted one: `ai_provider` defaults to `groq`. `Literal` still accepts `ollama` so an existing `.env` keeps working.
  3. Nothing about the local adapter is removed. `OllamaProvider`, `VULNIX_AI_BASE_URL`, `VULNIX_AI_NUM_CTX`, `VULNIX_AI_DISABLE_THINK` and the `Vulnix Edge` alias all stay, together with the tests that exercise them; those catalog tests now set `ai_local_enabled = True` explicitly, so the default path and the opt-in path are both covered.
  4. `Vulnix Edge` is out of severity routing. The `info` tier now prefers `Vulnix Sprint`, and the duplicate, unreferenced `_SEVERITY_ALIAS_ORDER` / `preferred_for_severity()` pair in `catalog.py` was deleted instead of revised — one severity map is easier to keep honest than two that disagree.
  5. A workspace that had chosen the local reviewer is not stranded. `selected_entry` already falls through requested → stored → server default, and a stale stored id resolves to nothing in the live catalog, so the audit continues on the configured hosted reviewer rather than failing. A test pins that behaviour.
  6. The env samples say what is on and what is off: `VULNIX_AI_PROVIDER=groq`, a new `VULNIX_AI_LOCAL_ENABLED=false` block with its rationale, and a note that the timeout and `NUM_CTX` names belong to the local adapter.
- **Alternatives considered:** deleting `OllamaProvider` and its settings (the user asked for "for now"; removal would make re-adding a reconstruction rather than a flag); listing local models and hiding them in the API layer (the probe would still run, and a catalog entry that exists but is filtered at the boundary invites a leak); keeping Ollama as the boot default with an empty picker fallback (a deployment that has not pulled a model then defaults to a reviewer that cannot answer); leaving `preferred_for_severity()` in place for a future caller (dead code that contradicts the map the agent actually uses).
- **Security implications:** with the gate off, no request is made to a localhost model endpoint from the catalog probe path, which removes one SSRF-shaped outbound call from the default configuration. A local reviewer an operator opts into remains bounded by the same prompt-size, output-cap and redaction rules as a hosted one. Aliases are unchanged: a local entry still surfaces as `Vulnix Edge` or a digest name, never a vendor tag.
- **Consequences:** the shipped catalog is hosted reviewers only, so a deployment with no hosted key shows an empty picker and `AI_DISABLED` rather than a local model nobody configured. Landing copy that advertised "Ollama (default) — fully local, zero egress" was replaced with the reviewer-coverage claim the code actually supports, and the FAQ answers with failover behaviour instead of a provider list. `Requirements & Specs/Vulnix_TECH_STACK.md` and `API_SPEC.md` now describe local inference as opt-in. Re-enabling costs one setting plus a re-read of the picker; nothing else has to be written again.

## ADR-018 — An example environment file is a placeholder file
- **Status:** Accepted
- **Context:** While updating the AI blocks in the env samples for ADR-017, `backend/.env.example` was found to carry a complete OpenRouter key in the shape the vendor issues (`sk-or-v1-` plus 64 hex characters) instead of the empty value every other credential in the file uses. The line is tracked and was committed, so it is in history as well as in the working tree. The key was pasted while documenting the reviewer chain in ADR-015 and no check caught it, because nothing in the repository reads the example file.
- **Decision:**
  1. The value is gone: the setting is empty and the line above it states that the real key belongs in `backend/.env`, which git ignores.
  2. Every tracked file was scanned for other credential-shaped values. The remaining hits are test fixtures for scanner output, which are synthetic by construction and stay.
  3. The committed value is treated as leaked, not as an inconvenience. It must be rotated or revoked at the vendor by its owner; the repository change alone does not un-publish it.
  4. No history rewrite was attempted. Reopening `013f96d` changes a commit other work sits on and is the owner's call, not a cleanup an agent performs quietly.
- **Alternatives considered:** leaving the key in place "because it is only a free-tier key" (the tier has no bearing on what a holder can spend or read); replacing it with a truncated version (a partial secret is still a secret and still trains the next person to paste one); silently running `git filter-repo` (irreversible, forces everyone to re-clone, and is exactly the kind of action that needs a human decision).
- **Security implications:** the exposure surface is the vendor account behind that key — request quota and any model listing tied to it. `AGENTS.md`'s rule that only placeholders may be committed is what this record enforces; nothing here changes how real credentials are handled at runtime, where they stay in the environment and never in a response, log or audit row.
- **Consequences:** one credential rotation is now an open action item for the owner, and the file is safe to copy again. A future pass over the example files should re-check them rather than assume, since the same paste-during-documentation mistake is what produced this one.

## ADR-019 — The audit console palette follows the theme
- **Status:** Accepted (revises the surface rule in ADR-012/ADR-013's console work; consistent with DESIGN.md's "default light, optional dark")
- **Context:** The audit run detail page was built as one dark operations surface, and it was built that way at the wrong layer. `.audit-ops` in `frontend/src/index.css` re-declared the whole token set (`--canvas`, `--background`, `--card`, `--popover`, `--primary`, `--border`, `--muted-foreground`, …) to dark hex values, unconditionally, plus `color-scheme: dark`, a dark radial glow and a dark drop shadow. Tokens are how every other console surface gets its colour, so the page's JSX — which contains no raw palette class at all — could not override them: switching to light changed every other `/app` page and left this one black. The same override caused a second, quieter fault. `dark:` utilities are gated on `.dark` on the root element, and `.audit-ops` never carried that class, so in light mode the popovers and menus inside the console (`components/ui/dropdown-menu.jsx` is the visible one) resolved their `dark:bg-*`/`dark:text-*` variants against light token values while sitting on a pinned-dark panel. The runs list and the findings list were token-driven and never had this problem, which is why the fault looked localized to one page.
- **Decision:**
  1. The ops palette is declared twice, and the light one is the base. `.audit-ops` carries the light emerald-tinted set, and `.dark .audit-ops` replaces it with the existing dark set, value for value. The console's identity is unchanged when dark is selected; light mode gets a real light version rather than a leftover.
  2. The decorative layers are variables too, not literals. The radial glow, the header's grid overlay and the panel shadow read `--ops-glow`, `--ops-grid` and `--ops-shadow`, each defined in both blocks, because a 6%-alpha mint glow that is right on near-black is invisible on near-white. The `.audit-terminal` scrollbar now uses `var(--border-strong)` instead of one hex.
  3. `color-scheme` is set explicitly per block (`light`, `dark`) so native scrollbars, form controls and date pickers inside the console follow it rather than the page default.
  4. The disagreement between tokens and `dark:` utilities is resolved by construction rather than by a class: the palette now keys off the same `.dark` root class that Tailwind's custom variant keys off, so nothing inside the console can be half-themed.
  5. The exception is documented in one line in DESIGN.md, next to the theme it respects: a surface may own a palette, no surface may pin one.
- **Alternatives considered:** adding the `dark` class to `.audit-ops` and calling the console dark-only (one line, and it fixes the popover mismatch — but it makes the theme control a lie on the page the user is most likely to be staring at, and DESIGN.md's stated default is light); restyling the page with plain tokens and dropping the ops identity (loses the one surface that is deliberately not a card grid); scoping the dark block under `.dark .audit-ops` only, with no light values (the base `:root` set is neutral slate and would strip the emerald identity from the light console); inlining the palette in JSX with a `style` prop (six more places that have to be kept in step with the token layer).
- **Security implications:** none. This is a presentation-layer change; no data, no endpoint and no untrusted string is involved. The severity ramp stays constant across themes by design — it carries meaning, not mood — so a colour change cannot make a critical read as low.
- **Consequences:** the light ops palette is a second set to maintain whenever a console token changes, and both blocks now have to be edited together; the comment above `.audit-ops` says so. Contrast was checked against the light values by hand (`--primary #047857` on `--card #ffffff` is 5.5:1, `--muted-foreground #4e6a5d` on `--canvas #e8f0eb` is 5.1:1, `--destructive #b42318` on white is 6.6:1). The audit console itself could not be observed rendered: `/app/**` is behind `ProtectedRoute` and no session is available to this agent, so verification was done against the built stylesheet with a scratch document that reproduces the page's class structure, and the populated page remains unverified visually.
- **Date / owner:** 2026-10-27 / audit detail not responding to the theme control.

## ADR-020 — A finished run is timed to its own end, not to the page load
- **Status:** Accepted
- **Context:** A live audit that failed in about seventy-five seconds reported `runtime 36m 39s` in the execution stream, which read as the retry loop overshooting `scan_total_timeout_seconds` (900 s by default). It was not. `ScanProgressTrace` derived its elapsed figure from a `now` state that is only refreshed while the run is live, so for any finished run `now` is the moment the component mounted and the number shown is "time since the run started, as of whenever you opened this page" — it grows every day the audit stays in the list, and a two-week-old audit would have displayed two weeks. The same component already had a correct sibling in `RunDuration` on the same page, which prefers `completed_at` and only falls back to the ticking clock. The step rows carry their own checkpoint timestamps, which is what made the contradiction visible: six checkpoints spanning just over a minute under a runtime that claimed half an hour.
- **Decision:**
  1. `ScanProgressTrace` takes `endedAt` and uses it whenever the run is not active; the ticking clock is reserved for live runs, where "elapsed so far" is the honest label. `AuditRunDetail` passes `scan.completed_at`.
  2. The fallback chain is `endedAt` → `now`, not `now` unconditionally, so a run that finished before this field was ever populated still shows a number rather than an em dash.
  3. No backend change. `started_at` and `completed_at` were already correct, `outcome.duration_ms` was already measured from the agent's own start, and the trace timestamps were already the worker's — only the arithmetic on the way to the screen was wrong.
- **Alternatives considered:** computing the runtime in the worker and shipping a `duration_seconds` field (the API already returns both endpoints, and a third value that can disagree with them is a new way to be wrong); hiding the runtime for finished runs (removes the symptom and loses the one number that tells an operator whether a refusal was fast or the audit ground slowly); relabelling it "since start" (accurate, but it puts a clock reading in a field the page calls runtime).
- **Security implications:** none directly. Indirectly this matters for triage: a misleading runtime was enough to make a correctly-failing audit look like a timeout bug, which is how attention gets spent on the wrong component.
- **Consequences:** the audit console's two duration displays now agree by construction. Verification is by reading the two code paths and by a clean lint and production build; the populated page could not be observed, since `/app/**` needs a session this agent does not have, so the corrected figure on a real failed run is unconfirmed. The underlying failure in that transcript is a separate matter and is not addressed here — `AI_MISCONFIGURED` on every file means the reviewer returned a non-retryable 4xx, and only `ai_provider_refused provider=… status=… reason=…` in the server log names it.
- **Date / owner:** 2026-10-27 / execution stream reported a runtime that the run never had.

## ADR-021 — The unit suite owns every reviewer credential it probes
- **Status:** Accepted
- **Context:** `Settings` loads `backend/.env` from the working directory, so a pytest run inherits whatever credentials the developer has configured. `tests/unit/test_ai_catalog.py` was written against exactly that hazard and blanks the primary, the fallback and the Gemini keys in its `enabled` fixture, with a comment saying a test for one reviewer must not borrow another's credential from the env file. OpenRouter was added to the reviewer chain later and the fixture was never told, so `_probe_openrouter()` found a live key, asked `https://openrouter.ai/api/v1/models`, and the stubbed transport raised `unexpected probe url` for every test that used the fixture. Two of those tests assert the opposite behaviour — that OpenRouter is *not* probed without its own key — so an operator's env file was silently inverting the suite's meaning. No egress happened: the fake transport refuses unlisted URLs, which is the property that turned this into a loud failure rather than a live request to a vendor from a unit test.
- **Decision:**
  1. The fixture blanks the OpenRouter credential alongside the other three, so a catalog test's notion of "configured" is set by the test and never inherited.
  2. It stays an assertion error rather than a fallback response. A probe the fixture did not stub means the test's own premise is wrong, and that must be loud; quietly answering every URL would let an unstubbed vendor call pass as green.
  3. Adding a reviewer to the chain now requires adding its credential to this fixture. The comment at the fixture says so, because the failure mode of forgetting is a red suite on someone else's machine, not a red suite here.
- **Alternatives considered:** an autouse conftest fixture that scrubs all `VULNIX_AI_*` env values before the app imports (more hermetic, but it would also change tests that legitimately assert on configured state and hides which suite depends on what); marking those thirteen tests skipped when no key is present (turns a real isolation bug into silence, and the skipped count becomes the new normal); setting `VULNIX_AI_OPENROUTER_API_KEY=` in `.env.example` guidance and telling developers to keep their unit environment key-free (a rule with no enforcement, and the reason the bug existed is that developers correctly put real keys in the file the app reads).
- **Security implications:** the operator's live OpenRouter credential was printed into pytest failure output while this was diagnosed — the traceback echoed the request headers, including the bearer token. It is a loopback-local artefact of a run on their machine, but the token should be considered exposed to anything that ingests that console output or log file. Nothing in the repository, its history, or any tracked example file contains it: the tracked key line is empty, which ADR-018 established and this change does not disturb.
- **Consequences:** the catalog suite is now independent of which reviewers the developer has configured, which is what makes its assertions about failover membership trustworthy. The broader hazard remains open by design: any test that reads `settings` still inherits `backend/.env`, so a future credential-shaped setting added to the chain is a future fixture edit.
- **Date / owner:** 2026-10-27 / a green suite on one machine, red on another, because of a key rotation.

## ADR-022 — A deployed console crosses into the API through a named allowlist
- **Status:** Accepted
- **Context:** On a laptop the console and the API are one origin: Vite proxies `/api` and `/health` to `localhost:8000`, so no browser ever applies cross-origin rules and nothing in the backend had to think about them. A deployment breaks that identity for a good reason — the console is static content best served from a CDN (Cloudflare Pages) while the API is a long-lived Python process (Render) — and the result is that every authorized call the console makes is cross-origin. Every one of those calls carries an `Authorization` header, which is not a CORS-safelisted header, so each one is preceded by a preflight that the API answered with a 404-shaped response and no `Access-Control-Allow-Origin`, and the browser reported it as a network error rather than a refusal. An unset allowlist is therefore not a neutral default in production; it is a console that cannot read its own data.
- **Decision:**
  1. `VULNIX_CORS_ALLOW_ORIGINS` holds a comma-separated list of exact browser origins (scheme and host, no trailing slash) and the API mounts `CORSMiddleware` only when the list is non-empty. Wildcards are not accepted, in code and in the setting's shape.
  2. `allow_credentials=False`. The token is set by the console's own fetch code, never a cookie the browser attaches on its own, so a credentialed cross-origin request has no legitimate purpose here — and accepting one would let any listed origin act as the visitor.
  3. The allowed request methods are the six the API actually routes (`GET`, `POST`, `PATCH`, `PUT`, `DELETE`, `OPTIONS`) and the allowed request headers are `Authorization`, `Content-Type` and `X-Request-ID`. `X-Request-ID` is the one response header exposed, because it is the value an operator quotes when reporting a failed call.
  4. The middleware is added before the request-context middleware so that request-context stays the outer layer. A preflight is answered by CORS middleware without reaching a route and carries no body, and it is exactly that response which most needs the `X-Content-Type-Options`, `X-Frame-Options` and `Referrer-Policy` headers the outer middleware applies.
  5. An empty list is still a supported configuration and keeps the previous behaviour: same-origin only, which is what the dev proxy, a server-side client and the test suite expect. Nothing had to be configured locally to stay local.
  6. `tests/unit/test_cors.py` asserts all four states — unset, listed origin (preflight and simple request), listed origin without a credentials header, and an unlisted origin getting nothing.
- **Alternatives considered:** `allow_origins=["*"]` (one line, and it makes any page on the internet able to read any user's findings with that page's own token — with a bearer token in play, a wildcard is not a convenience, it is a hole); deploying the console and the API under one hostname and routing by path, which would keep CORS unnecessary but ties a static CDN to a compute origin and puts a second reverse proxy in the failure path; a Pages Function proxying `/api` to Render (same origin from the browser's point of view, and it puts an extra hop that silently rewrites streaming uploads and doubles the timeout budget); putting the allowlist in the database per workspace (a configuration decision does not belong in the data the configuration is meant to protect).
- **Security implications:** This is the change that decides which browsers may read the API, so the list is a security boundary and not a convenience: adding an origin is a deployment decision, and preview URLs on a CDN are public addresses that anyone who guesses them can reach. Because the list is exact and credentials are off, a page that is not named gets an opaque network failure and no readable body. `max_age=600` bounds how long a browser may trust a preflight, which keeps a revoked origin at most ten minutes stale.
- **Consequences:** A deployment where the console and the API differ needs one variable set on the API side before the console can sign in, and `Requirements & Specs/DEPLOYMENT.md` says so in the order the values become knowable (the API gets its hostname first). Two origins for one product — a custom domain and its `*.pages.dev` alias — both have to be listed, and forgetting the second produces a console that works on one URL and not the other. The change is inert locally, so the local path is verified only by the tests that assert an unset list adds nothing.
- **Date / owner:** 2026-10-27 / a deployed console whose every authorized call failed before it reached the route.

## ADR-023 — Quarantined archives live in an S3-compatible bucket, not on the host
- **Status:** Accepted
- **Context:** `LocalStorage` writes under `VULNIX_STORAGE_LOCAL_ROOT` and that is fine on a laptop. It is wrong on every deployed shape for two independent reasons. A deployed instance's filesystem is rebuilt from the image at every deploy, so an archive uploaded last week is gone and the row that points at it now describes nothing — and the avatar written by one API instance is unreadable by the next one to serve the request. Worse, Vulnix is two processes: the API accepts the upload, the worker runs the audit. `app/scanning/pipeline.py` already re-opens the object by `upload.object_key` rather than trusting a path handed over, which is the property that makes a split deployment possible at all — but only if the key resolves to storage both processes can see.
- **Decision:**
  1. A deployed backend sets `VULNIX_STORAGE_BACKEND=s3` and points at a private S3-compatible bucket. The object key format, the server-side generation of keys, and the confinement rule are unchanged; only the medium moves.
  2. `VULNIX_S3_REGION` exists and defaults to `auto`. A signing region is mandatory for SigV4 even when the endpoint is spelled out in full, and boto3 raises `NoRegionError` before it opens a connection. R2 and the other compatible stores expect `auto`; plain Amazon S3 expects the real region name.
  3. The client is configured with `signature_version="s3v4"` and both `request_checksum_calculation` and `response_checksum_validation` set to `when_required`. Current boto3 attaches a CRC32 checksum trailer to every upload unless told otherwise, and R2 answers that trailer with a 400.
  4. Integrity is not being traded away for compatibility. `put_stream` still reads the stream once, hashing and counting the bytes itself, and it is that sha256 — the digest of the bytes this application agreed to accept — that goes on the upload row. The skipped trailer is boto3's second opinion, not the record.
  5. `put_stream` no longer buffers. It walks the stream in 1 MiB chunks for the size guard, rewinds, and hands the same seekable stream to `upload_fileobj` with a 5 MiB part size, so a 100 MiB archive is never resident in a 512 MB process. Both call sites already hand over a seekable object (a spooled upload file or an in-memory avatar), which is what makes the rewind legal.
  6. The `s3` extra is floored at `boto3>=1.34.117`, the release that accepts those two checksum options. boto3 stays a lazy import, so a deployment that never uses it does not pay for it.
  7. `tests/unit/test_storage_s3.py` substitutes the `boto3` module rather than skipping when it is absent, because the things being asserted — a region reaches the client, no trailer is configured, the hash matches the bytes actually sent, an oversize upload is refused before anything is transferred — are precisely the ones that cannot be caught by a filesystem test and are silent in production.
- **Alternatives considered:** a persistent disk on Render (fixes survival, not the two-process visibility problem, and it makes the API stateful in a way that forecloses horizontal scaling); re-uploading the archive from the browser to the bucket with a signed PUT (the right long-term answer for the size problem, and a new API surface, a new token flow and a new client path — recorded as a follow-up rather than folded into a deploy change); mounting the same volume into both services over a private network share (neither host offers one); keeping local storage and simply re-downloading from the object store every time (which is what the pipeline already does — the objection was never about reads, it was about the bytes having somewhere durable to live).
- **Security implications:** The bucket stays private. Nothing in it is ever handed to a browser: an archive is read server-side by the audit pipeline and by the reviewer path, and the console only sees an upload's metadata, so a compromised or guessed object key is not an access path. Keys are generated server-side from a project id and a UUID, so a client cannot aim a write at a path it does not own — the rule ADR-005 established and this change does not disturb. Turning off boto3's automatic trailer does not weaken the guard against a malicious archive: entry validation, size caps and the decompression ratio checks all run on the bytes after they are read back, whatever wrote them. Object storage is a second place a quarantined source tree now sits, so its credentials are scoped to that one bucket and grant read and write only.
- **Consequences:** A deployment is now a real multi-process system: an upload accepted by the API is only useful to a worker that can reach the same bucket, so a missing or misconfigured token is an intake failure rather than a worker failure, and the log line names which. Avatar URLs remain unguessable-name-only reads and now survive a rebuild. The 100 MiB archive still traverses the API process on the way in, which is the next thing to fix (see DEPLOYMENT.md's known limits). `LocalStorage` is untouched and stays the default, so tests and local runs do not need credentials, and no boto3 code path is exercised by them other than the stubbed unit tests.
- **Date / owner:** 2026-10-27 / an upload that would evaporate on the next deploy and be invisible to the process that had to scan it.

## ADR-024 — An audit is queued work, and the queue needs a sweeper to be whole
- **Status:** Accepted (implements ADR-003 on real infrastructure)
- **Context:** ADR-003 decided long ago that scans run in workers separate from the public API, and the code honours it: `enqueue_scan()` either runs the task inline (`VULNIX_CELERY_EAGER=true`, the default) or posts it to a broker. Eager mode is the whole deployment hazard. An audit of a repository is not a fast operation — `VULNIX_SCAN_TOTAL_TIMEOUT_SECONDS` defaults to 900 and a real run against a hosted reviewer legitimately spends minutes in it — while a deployed web instance cuts an HTTP request off at roughly 100 seconds. So an inline audit on a host like Render does not finish: the request dies, the process may be recycled with it, and the run is left in a state nobody owns. The same asymmetry already had a symptom in the integrations layer: `app/modules/integrations/service.py` refuses to claim a delivery whose `next_attempt_at` is still in the future, with a comment saying only the sweep may claim it later — and no scheduler existed to run that sweep, so a backed-off Slack or Jira notification waited forever in silence.
- **Decision:**
  1. A deployed backend runs with `VULNIX_CELERY_EAGER=false`. The API validates, persists and posts the job; it never performs the audit.
  2. The blueprint starts three processes: `vulnix-api` (uvicorn behind a `/health` check), `vulnix-worker` (`celery … worker --concurrency=1`), and `vulnix-scheduler` (`celery … beat`), plus one Redis instance shared by all three over the private network.
  3. Concurrency is one scan per worker process, deliberately. A worker unpacks an attacker-controlled archive, and a second concurrent scan on the same small instance buys throughput at the cost of a wider blast radius and an OOM that kills both. Capacity is added with more worker instances, not more threads.
  4. The beat schedule belongs to the Celery app, not to a host cron: `vulnix.drain_integration_outbox` every 60 seconds. `worker_prefetch_multiplier=1` and `task_acks_late=True` stay as they are, so a scan is not handed to a second worker while the first is still running it.
  5. `VULNIX_SCAN_WORKDIR` points at `/tmp`, and the extracted tree is treated as scratch that may vanish. Nothing may depend on it after the run, which was already true: the pipeline re-opens the archive from object storage (ADR-023) instead of trusting a path.
  6. Local and test behaviour is unchanged. Eager mode remains the shipped default so a developer can run the whole product with one process and no Redis, and `tests/unit/test_celery_schedule.py` pins both halves of `enqueue_scan` — inline when eager, posted when not — plus the existence of the schedule entry, so the sweep cannot be dropped again by a refactor.
- **Alternatives considered:** a Render cron service running the sweep with `celery call` (one more moving part and no better than a beat process that already knows the interval); raising the web request ceiling or faking progress with a streaming response (the ceiling belongs to the host, and a request that lies about finishing is how a run gets double-executed); running beat inside each worker with `--beat` (correct for one worker and a duplicate scheduler the moment there is a second, which is the first thing scaling does); Redis as the result backend replaced by polling the database (the scan row is already the source of truth for status; the result backend is Celery's own bookkeeping and is not load-bearing for the console).
- **Security implications:** The job payload is a scan id and nothing else, and the worker reloads and re-authorizes from the database, so a broker that someone else can write to cannot inject a scan over someone's project — the permission check happens in the worker, as it does in the API. Keeping the audit out of the request path also keeps the untrusted-archive work off the process that holds user tokens, which is the isolation ADR-003 wanted and eager mode quietly gave up. The queue itself is not a public surface: `ipAllowList` is empty, so only services in the same private network can reach Redis, and `noeviction` is chosen because a dropped queue message is a lost audit rather than a lost cache entry.
- **Consequences:** A deployment is four services, not one, and each failure mode now has a distinct symptom: `queued` forever means no worker, a dead `vulnix-scheduler` means notifications stop retrying with nothing on the API to say so, and a Redis restart on a free plan loses jobs that were never claimed while the scan row survives, so the audit looks stuck rather than lost. The API's own request budget is now only ever spent on validation and storage, which is what makes the console's timeouts mean something. The scan deadline (900 s default) is now a worker-side wall clock with no HTTP client attached, and cancellation continues to work by database flag rather than by killing a request.
- **Date / owner:** 2026-10-27 / an audit that could not outlive the request that started it.

## ADR-025 — The console deploys as static files with a history fallback and a build-time API origin
- **Status:** Accepted
- **Context:** The frontend is a React single-page app built by Vite: `dist` is HTML, hashed assets and a favicon, with no server component, no SSR and no runtime config lookup. Two properties of that shape decide the deploy target. The router owns paths like `/app/audits/scan-…` and `/signin`, but those paths do not exist as files, so a host that returns 404 for a missing file breaks every deep link and every refresh — which is the interaction a security reviewer uses constantly when pasting a finding link into a report. And `VITE_API_BASE_URL` is substituted by the bundler at build time (`frontend/src/lib/constants.js`), so the API's address is baked into the JavaScript rather than read when the page opens.
- **Decision:**
  1. The console is deployed as a static site on Cloudflare Pages — root directory `frontend`, build `npm ci && npm run build`, output `dist` — and no compute service runs for it. The Render blueprint deliberately contains no frontend service: a CDN is where a bundle of files belongs, and it is the same vendor whose object store already holds the archives (ADR-023).
  2. The SPA fallback is a real artifact in the repository, not dashboard folklore: `frontend/public/_redirects` holds `/* /index.html 200`, and Vite copies it into `dist`. Status 200 rather than 301 so the address bar keeps the deep link the visitor asked for.
  3. `frontend/public/_headers` carries the response-policy the API also uses — `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` — and one deliberate cache split: `index.html` is `max-age=0, must-revalidate` so a deploy is live on the next navigation, `/assets/*` is a year and `immutable` because Vite puts a content hash in every filename there.
  4. No `Content-Security-Policy` is shipped by this change. The animation layer writes inline styles on the elements it moves, so any policy that keeps it working has to carry `style-src 'unsafe-inline'`, and the PDF report export hands the browser a `blob:` URL. A policy that is wrong does not fail visibly: it removes a feature for signed-in users while previewing fine. It belongs in its own change with the console exercised behind it.
  5. The API origin and `NODE_VERSION` are Pages environment variables, and `VULNIX_CORS_ALLOW_ORIGINS` must name every origin this console is reachable on (ADR-022), including any `*.pages.dev` alias in use.
  6. `Requirements & Specs/DEPLOYMENT.md` is added as the runbook, with the order the hostnames become knowable spelled out (the API gets its address first, then the two cross-referencing variables), because a blueprint cannot know a subdomain the host assigns at creation.
- **Alternatives considered:** serving the console from the Render web service (one origin, no CORS at all — and it puts a static bundle behind a compute instance, forfeits the CDN, and makes every API deploy a frontend deploy); a Pages Function that proxies `/api` to Render (hides the cross-origin problem and adds a hop that re-streams every upload and doubles every timeout); rewriting to a server-rendered app (solves the fallback in the framework and rewrites the product's front end for a hosting detail); leaving the fallback to be configured in the dashboard (invisible, untestable, and the first thing that breaks when the project is recreated).
- **Security implications:** Static hosting means the console ships no server: there is nothing to patch between the browser and the API, and the headers file is the whole transport story on that side. The cache split has a security edge as well as a performance one — an HTML shell that must revalidate means a user is not left running an old bundle that predates a fix. Deep links into `/app/**` are shareable and carry no credentials in the URL; authorization stays in the bearer token, so a pasted finding link is safe to put in a report. `*.pages.dev` URLs are guessable and preview deploys are public, which is why the API allowlist is explicit about what may read data from them.
- **Consequences:** Changing the API's address needs a rebuild, not a restart, and a rollback of the console silently changes which API a bundle calls — worth knowing before a coordinated schema change. `_redirects` and `_headers` are Cloudflare-specific files living in `public/`; another static host would need its own equivalent, and DEPLOYMENT.md names them as the first place to look if a deep link 404s. Neither the Pages build nor the Render blueprint has been executed: these files are authored against the vendors' documented formats, and the first real deploy is what confirms the build settings, the prompted secret names and the fallback behaviour. No CSP exists yet, which is a stated gap rather than an oversight.
- **Date / owner:** 2026-10-27 / making the two halves of Vulnix actually deployable, and documenting what that costs.

## ADR-026 — CI tests the stack on Linux with no secrets, and its lint is honest about being debt
- **Status:** Accepted
- **Context:** Every statement in this repository that "the suite passes" has been produced by one human, on one Windows machine, running `backend/venv` by hand — and the deployed target is Linux, so the property that has never been tested is the one that matters most: does the suite pass where the product actually runs. Two known divergences sit in that blind spot. `app/scanning/adapters/base.py:134` has a `sandbox_env` whose non-`nt` half names `/usr/local/bin`, `/usr/bin` and `/bin` on the scanner's `PATH`, so that branch has never executed in a test run, and `tests/unit/test_archive.py:41` builds a ZIP entry with Unix symlink mode `0120777`, which Windows and Linux treat differently at extraction time. Meanwhile there was no `.github` directory at all, so nothing on a push could catch a regression, and `frontend/package.json` has no test runner, which means the frontend has no functional check except that it builds.
- **Decision:**
  1. One workflow, `.github/workflows/ci.yml`, two jobs. `backend` installs and runs pytest; `frontend` installs from the lockfile and builds. Both run on every push to every branch, on every pull request, and on manual dispatch, so a branch push and its PR check execute the identical file rather than two subtly different ones.
  2. The workflow needs no repository secret, and that is a property to preserve, not an accident. `backend/tests/conftest.py` pins the environment before the app is imported — in-memory SQLite, local temp storage root, `VULNIX_AI_ENABLED=false`, integrations off, Celery eager — so CI is more hermetic than a developer's machine, where `backend/.env` is read and ADR-021 had to defend against it. A CI job that needed a credential would be a CI job that reaches a vendor from a pull request.
  3. Versions are pinned to what the code is known to run on, not to what is newest: Python 3.14 (the interpreter the 375 tests pass under, and the one `render.yaml` pins) and Node 22 (what `Requirements & Specs/DEPLOYMENT.md` tells the Pages operator to set). The frontend build runs with `VITE_API_BASE_URL` unset, which resolves to `/api/v1` in `src/lib/constants.js`, so a CI bundle cannot carry a hostname into a cache that outlives the run.
  4. The backend installs `.[dev,postgres]` from `pyproject.toml`, not `backend/requirements.txt`. The deploy manifest deliberately carries no dev tooling and does carry `s3`, and installing boto3 in CI would change what the storage test proves: it injects a stub client into `sys.modules`, and the version of that code path which is green today is the one where no real boto3 exists.
  5. Lint runs in both jobs, annotated into the Checks tab (`--output-format=github`), and does not fail the run. `ruff check .` reports 9 findings in application code (6 auto-fixable) after `migrations/` is excluded in `backend/pyproject.toml` — the 16 findings generated Alembic files produce are its unsorted import block and its long `sa.Column(...)` lines, which is the generator's shape rather than anybody's style — and `npm run lint` reports 39 errors and 2 warnings across 14 files, none of them files this workflow introduces. A check that is red on every run is not a gate, it is background noise, and the cost of that noise is paid by the next real failure. `continue-on-error: true` is therefore set on exactly the two lint steps, with the counts and the rule breakdown recorded in `Requirements & Specs/TASKS.md`; the flip to blocking is one deleted line and is deliberately not free.
  6. Two cheap hardening defaults: `permissions: contents: read` at the workflow level, so a compromised build dependency cannot rewrite the repository or reach a broader token, and `concurrency` keyed on the ref with `cancel-in-progress`, plus job timeouts, so a burst of pushes does not queue stale runs and a hung test cannot occupy a runner.
  7. The frontend's build step is followed by an assertion that `dist/_redirects` and `dist/_headers` exist, because Pages parses those from the output directory rather than from `public/` (ADR-025) and a build that drops them ships a console whose deep links 404.
- **Alternatives considered:** blocking lint today (green-in-name-only, and it forces a behaviour change across 14 frontend files — including 6 `react-hooks/set-state-in-effect` findings that are logic, not style — inside the commit that adds a workflow); tagging the generated migration files with per-line `# noqa` or reformatting them (a marker added to silence a tool on code nobody authors by hand describes nothing, and the next `alembic revision` would need it again); a changed-files-only lint gate (green now and it blocks new debt, which is the right upgrade, but it depends on diffing against `github.event.before` or a PR base, and a wrong diff computation passes silently — the worst failure mode for a guard); running the suite against the Docker Compose Postgres and Redis from `infrastructure/` (the suite does not use them — it pins SQLite — so it would add two moving services and minutes of boot time to prove nothing); separate `backend.yml` and `frontend.yml` (more files, no more signal, and it lets the two drift on triggers and versions); adding a frontend test runner as part of this change (real and wanted, but it is a feature, not a CI decision, and belongs on the task list).
- **Security implications:** No secret exists in the workflow, so there is nothing here to leak into a pull request from a fork, and pytest cannot reach production: the database is in-memory, storage is a temp directory, reviewers are disabled, outbound integrations are off and the queue is eager. `contents: read` bounds what a build script can do with the automatic token. `npm ci` rather than `npm install` means CI installs exactly the reviewed lockfile instead of resolving a floating range on a runner. One gap is stated rather than closed: GitHub reports 5 Dependabot advisories (1 high, 2 moderate, 2 low) against the default branch, and this workflow does not fail on any of them. A dependency-audit gate is the honest next step for a product whose entire purpose is reporting other people's dependencies — but it needs a decision first about what a transitive advisory means for a build, which is not a workflow detail.
- **Consequences:** the first run executed on Linux and both jobs passed (Backend `ruff, pytest` and Frontend `eslint, build`, run 40650579036 at `1c906c3`), so the suite is not Windows-only and the fresh dependency resolve installs. What it did *not* do is prove the two Linux-specific paths named above: `sandbox_env()` runs only when a real CLI executable is invoked, which no test does, and `test_inspect_rejects_symlinks` asserts the archive is rejected at inspection, so the symlink entry is never created on either platform. Covering those is a test-writing task, not a CI one. Every push now costs about ten minutes of pytest (633 s locally) plus an install and a build; that is the price of the gate, and it is what makes `timeout-minutes: 30` a real bound rather than decoration. Two yellow lint annotations sit on every run until the recorded debt is paid, which is the visible cost of choosing signal over a clean board.
- **Date / owner:** 2026-10-27 / nothing has ever tested this stack except one laptop.
